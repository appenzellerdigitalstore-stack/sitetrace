How the domain inspector works

Traditional ICMP ping is blocked by most cloud providers, so it rarely tells you what you want to know about a real website. This tool uses HTTP fetch timing instead — the same path your browser actually takes — and runs DNS-over-HTTPS in parallel to resolve the IP. The result is a single, fast answer: where does this domain point, can I reach it, and how fast? For full DNS record details (MX, TXT, NS, SOA, …) see the dedicated DNS page.

    How to measure latency from a web browser — and why it's not the same as ICMP ping

    The classic ping command sends a single ICMP packet and measures the round-trip time — that's the gold standard for measuring the network path between you and a server. A web browser can't do that. Browser sandboxes don't expose raw socket APIs because that would let any webpage silently map the user's network. So the closest browser equivalent is an HTTPS request to the target, and the round-trip time on that includes DNS resolution, TCP handshake, TLS handshake, the server's response, and the page load.

    What the latency on this page actually measures. When you paste a URL and hit Inspect, the browser resolves the hostname via DNS-over-HTTPS (typically Cloudflare or Google — both fast), opens a TCP connection to the resolved IP on port 443, performs a TLS handshake (1-2 round-trips for TLS 1.3), sends the HTTP request, waits for the response headers, and reports the total time from fetch() call to response.headers received. That's what's shown as "ms" on the page. For most sites, DNS is ~30ms, TCP+TLS is ~50-150ms, and the server response is ~50-200ms — call it 200-400ms typical, with regional spikes from CDN edge assignment.

    ICMP vs HTTPS latency — what's different. ICMP ping measures just the round-trip time of a single network packet — usually under 50ms between major cities. HTTPS latency adds protocol overhead on top: DNS lookup (cached at the resolver usually, but still 1 round-trip on cache miss), TLS handshake (1 round-trip on TLS 1.3), plus the server has to do work and respond. The total is typically 2-5x higher than ICMP for the same path. Don't be alarmed if your HTTPS round-trip is 800ms to a server that ping shows as 80ms — it's normal.

    Why the latency varies so much. The network path is the same in theory (TCP and ICMP both travel over IP), but real-world latency varies for many reasons. (1) Routing asymmetry — your outbound route might be different from the inbound route, adding to total round-trip. (2) Congestion — peak hours on transcontinental routes add 50-200ms. (3) CDN edge assignment — your DNS might be picking a CDN edge far from you because the closest edge is overloaded. (4) TLS handshake size — a TLS handshake with a long certificate chain takes longer to verify. (5) HTTP/2 vs HTTP/3 — HTTP/3 (over QUIC, over UDP) has 0-RTT handshakes and significantly lower latency to first byte, but not all servers support it.

    What "good" latency is. Depends on what you're doing. For a static page load: under 100ms is excellent (single data center, CDN edge assigned to your city), 100-300ms is normal cross-continental, 300-500ms is sluggish but workable, 500ms+ feels broken. For interactive apps (games, video calls, remote desktops): under 30ms is the only thing that doesn't feel laggy. For backend microservices: under 10ms is the target, 10-50ms is OK for non-critical paths, anything above 50ms means something's wrong. The numbers here are full HTTPS round-trip — for true server-side latency you need distributed monitoring from multiple geographic regions.

    Why the multi-server ping below is useful. Pinging the same service from 9 global regions over time tells you about CDN edge assignment, regional outages, and routing shifts. If US-East is 80ms and US-West is 240ms, your traffic is going to a US-East CDN edge — which is fine if you're on the East Coast but bad if you're in California. If US-East pings and EU-Frankfurt doesn't, there's a routing problem between Cloudflare and your ISP in Europe. The pattern over time is more useful than any single ping. Press Start to begin polling; the results accumulate and you can spot trends.

    What CORS error means. If the response shows "reachable (response not readable)" or status shows "unknown", the request went out but the browser can't read the response. Why? CORS — Cross-Origin Resource Sharing. The browser asks the server "can I read your response from this domain?" via the Access-Control-Allow-Origin header. If the server doesn't respond with a permissive header (or doesn't respond at all because it crashed), the browser refuses to expose the response body. We can still tell you the request reached the server — that's why reachability is true but status is unknown. The actual response is at the server, just locked away from your browser.

    Why this isn't a real ping. ICMP ping uses the ICMP protocol (IP protocol number 1) which is a separate protocol from TCP and UDP. The browser sends TCP packets (IP protocol 6) over the same underlying network, but the path can vary (different routing rules), the server's response is different, and the timing includes all of TCP's overhead. For a true ICMP test, run ping example.com from your terminal — you'll see numbers typically 2-5x lower than what this browser tool shows. Use ICMP for "is the path healthy?" and HTTPS for "is the site actually serving content?"

    The checks behind this page happen entirely in your browser. The DNS resolution uses the public DoH endpoints (Google or Cloudflare), the HTTP fetch is a regular browser fetch with the timing captured at the response headers event. No data leaves your machine. If you want this from a script or CI:

    $ curl -w '%{time_starttransfer}s\n' -o /dev/null -s https://example.com
    # → 0.234s

    For batch probing of many URLs, the API at api.sitetrace.it.com has POST /api/status-check:

    $ curl -X POST https://api.sitetrace.it.com/api/status-check -H 'Content-Type: application/json' -d '{"urls":["https://github.com","https://discord.com"]}'
    # → [{url, status, latency_ms, content_type, redirect_url?}, ...]

    The free tier allows 100 calls per day with no signup. For continuous monitoring (poll a list of services every 30 seconds), use this page in your browser or wire up your own cron job against the API. The numbers in this browser are the same numbers the API returns, computed the same way.

    Frequently asked questions

    What does the domain inspector do?

    It runs three checks against a hostname in one shot: it resolves the IP addresses via DNS-over-HTTPS, attempts an HTTP fetch from your browser to measure reachability and round-trip time, and reports the result. The DNS record details live on the dedicated /dns-tools/ page.

    Why does the reachability sometimes show "unknown"?

    Some websites block cross-origin reads of their responses (CORS). When that happens, the browser still tells us the request completed — so we can usually mark the site reachable — but we cannot read the response body or status code. In that case the result shows "reachable (response not readable)".

    What is a good HTTP latency?

    Under 100 ms is excellent for most websites. 100-300 ms is typical for cross-continental connections. Over 500 ms will feel sluggish. The number you see is the full request round-trip from your browser, including DNS, TCP, TLS, and the server's response time.

    Why is DNS not shown on this page?

    The /dns-tools/ page is dedicated to that — it queries every record type (A, AAAA, MX, TXT, NS, CNAME, SOA) at once and renders a grouped view. The domain inspector here only needs the resolved IPs to do the HTTP check, so the rest stays out of the way.

    What is the live multi-server ping below?

    A power-user feature: add any URL you want to monitor, set a polling interval, and the tool will keep pinging each one from your browser. Polling only happens when you press Start, and only targets you — no central server, no third-party pings. The 9 popular services shown by default are just examples; you can remove them and add your own.
