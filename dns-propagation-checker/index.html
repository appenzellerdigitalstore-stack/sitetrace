What is DNS propagation?

DNS (Domain Name System) is the internet's address book — it translates human-readable names like example.com into IP addresses. When you change a DNS record, the change does not appear everywhere at once. Each DNS resolver caches the previous answer until the record's TTL (time to live) expires, then it asks the authoritative server again. This staggered refresh is what people call "DNS propagation".

    Why DNS changes take time to propagate

    Resolvers around the world cache DNS answers to reduce load on the authoritative servers. Each cached answer comes with a TTL set by the authoritative server. While the TTL is valid, the resolver returns the cached answer without re-querying. Once it expires, the resolver asks again and gets the new record.

    DNS propagation is the time it takes for a DNS record change to reach every resolver in the world. It's not one thing — it's the staggered expiration of caches. The authoritative server publishes the new record immediately. Every resolver that has the old record cached will keep serving it until its TTL expires, then it'll ask the authoritative server again and get the new record. With millions of recursive resolvers (every ISP, every company's DNS, every public resolver like 8.8.8.8 and 1.1.1.1), the staggered refresh means you can have a 5-minute window where some resolvers return the new record and others return the old.

    The TTL controls everything. Each record has a TTL field in its parent zone. The TTL is the number of seconds a resolver is allowed to cache the answer before re-querying. The authoritative server sets it when it publishes the record. Common TTLs are 300 seconds (5 minutes), 3600 (1 hour), 7200 (2 hours), 86400 (24 hours), and 172800 (48 hours). The TTL is a promise to the resolver: "you can cache this for X seconds, I'll have the answer ready when you come back." If the actual change happens before the TTL expires, the resolver doesn't notice — it just serves the cached answer.

    The 48-hour upper limit is a myth (mostly). Old advice said "DNS propagation can take 24-48 hours." That's true only for records with TTLs of 24-48 hours AND resolvers that have the old record cached. If your TTL is 300 (5 minutes), the worst-case propagation is 5 minutes after you change the record, not 48 hours. The 48-hour figure was real in the early 2000s when many authoritative servers used 48-hour TTLs by default and ISPs cached aggressively. Today, most authoritative servers default to 5-minute to 1-hour TTLs, and most resolvers respect them.

    How to speed up propagation. Three steps. (1) Lower the TTL on the record 24-48 hours before the change. So if your TTL is currently 86400, lower it to 300 first, wait 24-48 hours for the new TTL to propagate, then make the change. After the change, the worst-case propagation is 5 minutes. (2) Make sure your registrar or DNS provider's SOA refresh timer is reasonable — the SOA refresh field is the time after which a secondary nameserver asks the primary whether anything has changed. If it's 24 hours, secondaries take up to 24 hours to refresh. (3) For mission-critical DNS updates (DNSSEC rollovers, root key changes), some operators use the "refresh-from-vercelor" technique: lower it to 60 for several days, make the change, raise it back. It's paranoid and correct.

    Why different tools show different results. Each tool uses different resolvers. Your ISP's resolver, Cloudflare's resolver (1.1.1.1), Google's resolver (8.8.8.8), Quad9's (9.512.9.512), OpenDNS's, AdGuard's — they don't share records, they only share. Each one independently walks the DNS hierarchy when its cache is empty and independently caches for its own TTL countdown. If your tool queries 8 public resolvers and 7 have the new record but 1 has the old, propagation is 7/8 complete — give it another minute or two.

    NXDOMAIN lag during registration. When you register a new domain, the TLD nameserver needs to learn about your delegation, then resolvers around the world need to walk to your nameservers, and only then do they cache the answer. Negative caching (the absence of a record) is cached too — for the duration of the SOA's "minimum TTL" field, which is 300 seconds by default but can be longer. So a freshly-registered domain can show NXDOMAIN on some resolvers for a few minutes while others return SERVFAIL. After the negative cache expires, the resolvers re-walk and pick up the new delegation.

    TTL gotchas. CDNs often override the authoritative TTL with their own. Cloudflare, Fastly, and Akamai all set their own TTLs based on their caching logic — your authoritative 300-second TTL becomes a 5-minute or 24-hour TTL when served through Cloudflare's edge. This is normal and expected, but it means your changes might not be visible to users on those CDNs until the CDN's TTL runs. DNSSEC-signed zones also need their signatures to be re-generated when records change — the parent zone has a DS (Delegation Signer) record that points to your zone's key, and signatures on individual records need to be valid until their own expiry.

    The 8-resolver parallel check behind this page happens in your browser. We use the public DoH endpoints that each resolver publishes (Google at dns.google, Cloudflare at cloudflare-dns.com, Quad9 at dns.quad9.net, etc.) and run them in parallel with a small concurrency cap to respect rate limits. If you want the same check from a script or CI, the data is at api.sitetrace.it.com:

    $ curl -X POST https://api.sitetrace.it.com/api/dns-propagation -H 'Content-Type: application/json' -d '{"domain":"example.com"}'
    # → {resolvers: [{name, answers: {a: [...], ...}, ttl: 300}, ...], propagated: 7/8}

    If you want to query a specific one, the CLI equivalents are dig +short example.com @8.8.8.8 (Google), dig +short example.com @1.1.1.1 (Cloudflare), or dig +short example.com @9.9.9.9 (Quad9). Each one independently returns its current cached answer. If 7/8 of them agree and one doesn't, the dissenter is the one with the stale cache — wait for its TTL to expire.

    Frequently asked questions

    How long does DNS propagation really take?

    For most records with a short TTL (5–60 minutes), propagation is fast — most resolvers refresh within an hour. For records with a long TTL (12–48 hours) or for large TTL changes, propagation can take up to 48 hours to fully complete across the global resolver fleet.

    Why do different DNS lookup tools show different answers?

    Each tool uses different upstream resolvers (Google, Cloudflare, OpenDNS, ISP resolvers, etc.) and each resolver caches answers independently. Until the TTL expires on a given resolver, it returns the cached answer.

    Can I speed up DNS propagation?

    Not directly — propagation is governed by the TTLs already in the wild. But you can lower the TTL on a record 24–48 hours before the change so that the next refresh happens quickly.

    What is DNS-over-HTTPS?

    DNS-over-HTTPS (DoH) encrypts DNS queries so that no one on the path between you and the resolver can see what domains you are looking up.
