    How DNS lookups actually work

    DNS (Domain Name System) is the internet's address book. When you type example.com into a browser, DNS translates that human-readable name into the IP address the computer actually needs to connect. This page queries every common record type — A, AAAA, MX, TXT, NS, CNAME, SOA — in parallel and groups the answers for easy scanning. Queries are sent over DNS-over-HTTPS (Google + Cloudflare) so your lookups are private.

    When you type example.com into a browser, the browser asks the operating system to resolve it. The OS sends a DNS query to the configured resolver — typically your ISP's resolver, though you can override it (Cloudflare's 1.1.1.1 or Google's 8.8.8.8 are common choices). The resolver already has the IP for popular sites cached. If it doesn't, it walks the DNS hierarchy from the root: . → com. → example.com. Each level tells the resolver where to ask next. The whole walk takes 20-200ms for an un-cached record, or under 5ms if the resolver already has it.

    Record types. DNS is more than just "name → IP". The full vocabulary:

    • A — maps a name to an IPv4 address (e.g. 93.184.216.34). The most common query; what the browser uses to actually connect.
    • AAAA — same, but for IPv6 (e.g. 2606:2800:220:1:248:1893:25c8:1946). Modern networks query both A and AAAA and connect over whichever works.
    • MX — the mail servers that accept email for the domain. Mail is special: it doesn't follow HTTP redirects or load-balancer rules. The MX record points to specific servers (usually with priority numbers — 10, 20, 30).
    • TXT — arbitrary text. Originally for human-readable notes, now used for domain verification (Google Search Console, Microsoft 365, Facebook), email policy (SPF, DKIM, DMARC), and arbitrary DNS-based challenges.
    • NS — the authoritative name servers for the domain. These are the servers that hold the canonical records; the resolver asks them directly.
    • CNAME — an alias from one name to another. www.example.com is often a CNAME to example.com. CNAMEs can't coexist with other records at the same name (a "CNAME at the apex" rule, though Cloudflare and Route53 have workarounds).
    • SOA — administrative info about the zone (serial number, refresh/retry/expire timers, admin contact). The serial is the key field — it's how secondary name servers know whether to refresh.
    • CAA — which Certificate Authorities are allowed to issue certificates for the domain. Added after a few high-profile mis-issuances.
    • TLSA — for DANE, which pins TLS certificates to DNS. Mostly used in SMTP setups that want to skip the CA system.
    • PTR — the reverse lookup — IP to name. Used by mail servers to verify that a sending IP is who it says it is.

    Why DNS-over-HTTPS matters. Plain DNS (port 53) is unencrypted. Every device on the path between you and the resolver — your router, your ISP's transit, your ISP's recursive resolver, the upstream — can see every domain you look up. Your ISP can (and often does) log this and sell it to ad networks. DoH encrypts the query so the path can't see the domain. The resolver still can — Google and Cloudflare see your queries — so DoH only protects you from path observers, not from the resolver itself. Cloudflare commits to deleting query logs within 24 hours; Google's transparency report shows their retention policies.

    Why DNS propagation is slow. Each record has a TTL (time-to-live) — typically 300 to 86400 seconds. Resolvers respect the TTL and only refresh after the record expires. If you change an A record and the old TTL was 86400, resolvers will keep returning the old IP for up to 24 hours. Best practice: lower the TTL 24-48 hours before a planned change, do the change, then raise it back. Some CDNs and cloud providers let you set per-record TTL globally from their dashboard; others require editing each record.

    Where DNS lives. The five regional registries (ARIN, RIPE NCC, APNIC, LACNIC, AfriNIC) own the IP space and delegate the reverse zones. The root zone (.) is operated by Verisign under contract with ICANN and contains the TLD nameservers (.com, .org, .net, .uk, etc.). The TLDs delegate each registered domain to the authoritative nameservers (often Cloudflare, Route53, or a hosting provider's DNS). This delegation is itself stored in DNS as NS records.

    Why you might see different answers from different resolvers. Caching. A fresh record change might appear in Google but not in Cloudflare if Google's cache hasn't expired. CDN-based DNS (Cloudflare, NS1, Route53 with latency-based routing) returns answers based on the resolver's location — a domain on Cloudflare's CDN can show different IPs from different resolvers because the resolver and the user are in different places. That's normal, not a misconfiguration. Split-horizon DNS (where internal vs external answers differ) is also a thing, especially on enterprise networks — your office Wi-Fi might resolve internal.example.com to a private IP while an external DNS resolver returns NXDOMAIN.

    The lookups behind this page happen in your browser. We use the public DoH endpoints that Google and Cloudflare publish at https://dns.google/resolve and https://cloudflare-dns.com/dns-query. Both resolvers return the answer in JSON, which we parse and render. No server we operate sees your query. If you want the same lookups from a script or CI, the same data is at api.sitetrace.it.com:

    $ curl -X POST https://api.sitetrace.it.com/api/dns-lookup -H 'Content-Type: application/json' -d '{"domain":"example.com"}'
    # → {a: [...], aaaa: [...], mx: [...], txt: [...], ns: [...], cname, soa}

    If you want to verify directly against the authoritative nameservers without using a public resolver, the CLI equivalent is dig +short example.com A @8.8.8.8 (for A records against Google) or nslookup -type=MX example.com 1.1.1.1 (for MX against Cloudflare). Both return the same answers this page shows, with the same caching behavior — the resolver caches, you see the cached answer.

    Frequently asked questions

    What is a DNS lookup?

    A DNS lookup is a query sent to a DNS resolver asking for the records associated with a domain name. The most common query is for the A record (the IPv4 address), but DNS also stores AAAA (IPv6), MX (mail servers), TXT (verification and policy), NS (name servers), CNAME (alias), and SOA (zone authority) records.

    What are the different DNS record types?

    A maps a name to an IPv4 address. AAAA maps to IPv6. MX lists mail servers for the domain. TXT stores arbitrary text, commonly used for domain verification (Google, Microsoft, Facebook) and email policies like SPF/DKIM/DMARC. NS lists the authoritative name servers for the domain. CNAME creates an alias from one name to another. SOA holds administrative information about the zone.

    Which record type should I look up?

    You don't have to choose — this tool queries every common record type at once. For "where does this domain point," look at A and AAAA. For "where does its email go," look at MX. For "who runs this domain's DNS," look at NS. For "is this domain verified by Google/Microsoft/etc.," look at TXT. For "is this subdomain an alias of something else," look at CNAME.

    What is DNS-over-HTTPS?

    DNS-over-HTTPS (DoH) encrypts DNS queries so that no one on the path between you and the resolver can see what domains you are looking up. Traditional DNS sends queries in cleartext, which means your ISP, coffee-shop Wi-Fi, or anyone else on the network can log every site you visit. This tool uses DoH (via Google and Cloudflare) so your lookups are private.

    Why are my DNS records different from what I configured?

    DNS changes take time to propagate. Most resolvers respect the TTL (time to live) on each record and refresh from the authoritative server when it expires. Typical propagation is minutes to a few hours, but in some cases it can take up to 48 hours. If you just changed a record, wait and look up again later.
